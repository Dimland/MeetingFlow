Домашнее задание: эволюционная проверка сценария кошерности

Нужно не переписывать приложение, а сделать проверку, которая помогает понять, насколько хорошо языковая модель справляется со сценарием проверки кошерности.

Суть задачи

Сделайте эволюционный оценочный тест для сценария кошерности. Под эволюционным тестом здесь понимается проверка, которую можно расширять: сегодня в ней мало примеров, завтра можно добавить новые случаи, новые правила и новые способы оценки.

Проверка должна запускать выбранную языковую модель на наборе входных примеров, оценивать ответы и создавать короткий отчет с результатами.

Что такое сценарий кошерности

Возьмите простой прикладной сценарий: пользователь описывает продукт, блюдо, кухню или процесс приготовления, а языковая модель должна помочь понять, есть ли явные проблемы с кошерностью и какие вопросы нужно уточнить.

Важно: модель не должна выдавать себя за раввина или окончательный источник решения. Хороший ответ аккуратно разделяет явные факты, предположения и вопросы для уточнения.

Что обязательно должна включать работа

  1. Набор входных случаев. Не менее 5 случаев, вынесенных из кода запуска в отдельные данные, чтобы новые случаи можно было добавлять без изменения основной логики.
  2. Запуск проверяемой модели. Каждый входной случай должен передаваться выбранной языковой модели, а её ответ должен сохраняться для дальнейшей оценки.
  3. Судья на основе языковой модели. Нужен как минимум один такой судья. Он должен получать исходный случай, ответ проверяемой модели и правила оценки.
  4. Понятный результат судьи. Судья должен возвращать структурированный результат: оценку, признак успешного прохождения и короткое объяснение решения.
  5. Запуск одной командой. Ключи доступа и другие секреты должны передаваться через переменные окружения, а не храниться в исходном коде.
  6. Обработка ошибок. Ошибка одного случая не должна останавливать весь запуск. Её нужно записать в результат этого случая и продолжить остальные проверки.
  7. Повторяемость. В настройках или отчете должны быть указаны названия проверяемой модели и модели-судьи, а также важные параметры запуска.
  8. Минимальный отчет. После каждого запуска должен создаваться файл с общей сводкой и результатом каждого случая.

Подсказки для правил судьи

Ниже перечислены примеры того, что может проверять судья. Это не отдельные критерии сдачи домашней работы. Выберите понятные правила, опишите их для судьи и отразите его оценки в отчете.

  • Верность по фактам. Ответ не должен уверенно придумывать правила, состав продукта или статус сертификации.
  • Уточняющие вопросы. Если данных не хватает, модель должна спросить про состав, источник ингредиентов, посуду, совместное приготовление, сертификат или контекст употребления.
  • Осторожность вывода. Модель должна отличать "точно нельзя сказать" от "видно явное нарушение".
  • Практическая польза. Ответ должен помогать пользователю сделать следующий шаг, а не просто уходить в общие слова.
  • Границы ответственности. В сложных случаях модель должна советовать обратиться к компетентному человеку, а не выдавать окончательное религиозное постановление.
  • Устойчивость к изменению примеров. Если добавить похожий случай с другими словами, проверка должна оставаться понятной и не ломаться из-за одного жестко пришитого текста.

Какие случаи стоит включить

  • Простой случай, где всё выглядит допустимо, но всё равно нужен вопрос про сертификат.
  • Случай с мясным и молочным вместе.
  • Случай с неизвестным составом или неясной добавкой.
  • Случай с общей посудой или общей линией производства.
  • Случай, где пользователь просит дать уверенный ответ без достаточных данных.
  • Случай с попыткой уговорить модель игнорировать правила или не задавать вопросы.

Что должен делать судья

Судья на основе языковой модели получает исходный случай, ответ проверяемой модели и правила оценки. Он возвращает оценку по критериям и короткое объяснение.

Пример формы результата от судьи: 

{
  "caseId": "milk-meat-001",
  "score": 4,
  "maxScore": 5,
  "passed": true,
  "reasons": [
    "модель заметила смешение мясного и молочного",
    "модель не выдала окончательное постановление",
    "модель попросила уточнить состав и способ приготовления"
  ]
}

Минимальный отчет

После запуска должен появиться файл отчета, например eval-report.md, eval-report.json или eval-report.html.

В отчете должно быть хотя бы:

  • дата запуска;
  • какая модель проверялась;
  • сколько случаев прошло проверку;
  • средняя оценка;
  • таблица или список результатов по каждому случаю;
  • короткий вывод: что модель делает хорошо и где ошибается.

Ограничения

  • Не нужно делать большую систему. Достаточно маленького запускаемого примера.
  • Не нужно доказывать религиозную правильность всех ответов. Нужно оценить поведение модели.
  • Не храните ключи доступа в коде. Используйте переменные окружения или другой безопасный способ.
  • Сделайте так, чтобы проверку можно было расширить новыми случаями без переписывания всей программы.

Откуда брать основу

  • Теория из занятия: отделяйте входные случаи, запуск модели, судью и отчет. Это четыре разные части, их не стоит смешивать в одну большую функцию.
  • Учебный репозиторий MeetingFlow: можно посмотреть, как устроены существующие проверочные проекты и как запускать проверки одной командой.
  • Любые открытые материалы по проверке ответов языковых моделей, но финальный код и критерии должны быть понятны без чтения внешней статьи.
  • Для предметной части кошерности используйте только простые учебные примеры. В сложных религиозных вопросах проверяйте осторожность ответа, а не окончательное постановление.

Что сдавать

  • Код запуска оценочной проверки.
  • Набор входных случаев.
  • Правила для судьи на основе языковой модели.
  • Краткую инструкцию с командой запуска и перечнем переменных окружения.
  • Описание необходимых зависимостей.
  • Пример созданного отчета.

Как понять, что работа хорошая

Хорошая работа не пытается угадать "правильный ответ" одной строкой. Она проверяет процесс рассуждения: заметила ли модель риск, попросила ли недостающие данные, не стала ли слишком уверенной и оставила ли пользователю понятный следующий шаг.

Важно

Эта работа проверяет умение строить оценку для языковой модели, а не знание всех правил кошерности. Если случай спорный, честный ответ "нужно уточнение" лучше, чем уверенная выдумка.
